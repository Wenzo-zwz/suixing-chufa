## 已修复的 P2：旧房间保留的候选可绕过现在的预算规则

位置：`prototype/domain.mjs` 的预算过滤（约第103行）、`RoomStore.importRecord`、`ready`、`draw`；`server/cloud-api.mjs` 的 `loadRoom`。

数据库中的旧房间保存了完整的 `room.candidates` 快照。`importRecord` 原样接收旧快照，随后 `read`、`ready`、`draw` 均不根据当前目录重算候选。因此部署新库后，尚未抽签的旧房间仍能用已经删除的演示费用通过预算条件；前端随后把结果按 ID 升级为费用未知的真实资料，并不能修复实际抽签资格。

定点复现：通过 `git show` 读取基线目录，以旧目录创建 `preset: explore, maxBudget: 380` 的两人房间并全部准备；把导出记录导入使用新目录的 `RoomStore`。当前单人 `candidatePool` 返回0个候选，但导入房间仍为 `ready`、保留19个候选，且成功抽出长沙，服务端结果仍含演示预算180—380元。

建议：在旧目录房间加载/恢复时，对未抽轮次重新评估当前目录；候选资格变化时取消准备并更新版本，使用现有数据库并发机制持久化。已抽轮次应保留既有唯一结果，再按稳定 ID 更新展示资料。补充上述跨版本房间回归。

修复回查：`importRecord` 对未抽轮次按当前目录重算候选，候选完整资料变化时递增版本、清除准备并恢复 collecting；已抽轮次保持原记录与幂等结果。GET通过既有CAS更新路径持久化迁移，成员校验失败发生在数据库写入前。两个并发GET只有一个CAS迁移成功，另一个重试读取赢家状态，不重复增加业务版本。

重新执行最初的真实基线目录复现：预算条件下候选19→0，phase ready→collecting，version 2→3，旧版本抽签返回 VERSION_CONFLICT。另执行三项新增定点Node测试：旧房间费用资格及准备失效、已抽结果不变、并发GET单次CAS/外人禁止写入，3项全部通过。未发现修复引入新的并发或身份暴露问题。
